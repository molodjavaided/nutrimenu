# AI-SAFE — безопасность ИИ-агентов

Скилл моделирования угроз и hardening'а ИИ-агентов по **AI-SAFE v1.0**. Принципы нейтральны
(OWASP/NIST/MITRE), примеры — на стеке NutriMenu (Next.js + Vercel + Postgres/Neon через Prisma +
Gemini/Perplexity/Claude + Telegram-webhook + Upstash rate-limit), но скилл работает и на другом стеке.

**Профили угроз, релевантные NutriMenu** (недоверенный ввод в LLM):
- **AI-импорт ТТК** — текст/Excel/PDF/фото от владельца парсятся LLM (`lib/importer.ts`, роуты
  `parse-ttk`/`validate-ttk`/`parse-pdf-ttk`/`sheets`): prompt injection через содержимое ТТК,
  denial-of-wallet без гейта тарифа/rate-limit ([[feedback-ai-must-be-gated]]).
- **Barcode lookup** — штрихкод → внешний поиск (OpenFoodFacts) → AI-fallback (`lookup-barcode`):
  данные из внешнего API идут в промпт как «данные», не «команды».
- **Telegram-бот** — публичный webhook (`/api/telegram/webhook`, брифинг + переписка + sales-lead):
  проверка `X-Telegram-Bot-Api-Secret-Token`, ввод пользователя в роли `user`, лимит вызовов.

## Когда какой режим
- Есть код/проект и надо проверить → **AUDIT**.
- Начинаем новый ИИ-агент или добавляем модуль → **SCAFFOLD**.
- Если непонятно — спроси одним вопросом, что нужно.

## Справочники (читать перед работой)
- `references/threat-matrix.md` — 18 контролей по 5 уровням: риск, нейтральный принцип, реализация (примеры под MyResult-стек — читать как образец, транслировать на NutriMenu: Prisma вместо Supabase RLS, api-guard/Upstash вместо своего rate-limit), **сигналы для аудита** (что грепать). Главный файл.
- `references/checklist.md` — 15-шаговый практический чек-лист (основа SCAFFOLD).
- `references/catalogs.md` — OWASP LLM/MCP/Agentic + RAG, маппинг на контроли AI-SAFE, реальные инциденты.

5 уровней (снаружи→внутрь): **1 INPUT** (интерфейс) · **2 EXEC** (инструменты) · **3 INFRA**
(инфра/оркестрация) · **4 LOGIC** (ядро/рассуждения) · **5 DATA** (память/знания).

## Режим AUDIT

Цель — честная картина: что закрыто, что нет, что чинить первым. Не выдумывай покрытие —
если контроль не нужен проекту (нет RAG → DATA.3/4 = N/A), помечай N/A, не штрафуй.

**Шаги:**
1. **Профилировать проект.** Определи компоненты агента: где LLM-вызовы, какие инструменты/действия наружу, есть ли RAG/векторная база, память, публичные эндпоинты (вебхуки/формы), где секреты, мультиагентность. Используй Grep/Glob, не догадки.
2. **Пройти 18 контролей.** Для каждого из `threat-matrix.md` определи статус: **✅ есть / ⚠️ частично / ❌ нет / N/A**. Подтверждай каждый вывод **доказательством — `файл:строка`**. Используй секцию «Аудит — искать» каждого контроля как чек.
3. **Оценить уровни.** Балл 0–10 на уровень (доля закрытых контролей с весом по риску). Композитный балл = среднее по релевантным уровням. Не учитывай N/A.
4. **Приоритизировать.** Сортируй находки по риску из матрицы: `high×high` сверху. Каждая находка: контроль (YAISAFE.ID + кросс-ссылки), что не так, доказательство, конкретный фикс под стек, оценка усилия (S/M/L).
5. **Отчёт.** Сгенерируй `SECURITY-AISAFE.md` по шаблону `references/report-template.md` (scorecard + находки + план). Покажи краткую сводку в чате.
6. **Предложить фиксы.** Спроси, применить ли top-N правок (по убыванию риска) — атомарно, с перепроверкой. Не применяй без подтверждения.

**Точность важнее широты.** Лучше 6 уверенных находок с `файл:строка`, чем 20 догадок.
Не помечай контроль закрытым «на вид» — открой код и проверь.

## Режим SCAFFOLD

Цель — новый ИИ-агент с безопасными дефолтами с первого коммита. Не over-engineering:
раскатывай контроль, только если соответствующий компонент в проекте есть.

**Шаги:**
1. **Уточнить стек и компоненты** (дефолт — стек NutriMenu: Next.js API-роуты + Prisma/Neon + Gemini/Perplexity/Claude + Telegram-webhook): язык/фреймворк, есть ли инструменты/действия наружу, RAG, публичные эндпоинты, мультиагентность. Один блок вопросов, не больше.
2. **По чек-листу** (`checklist.md`) для каждого релевантного уровня заложи минимальный контроль:
   - INPUT: схема-валидация тела (Zod/Pydantic), фильтр инъекций, ввод в роли `user`, rate-limit, обрезка длины, валидация вывода (схема + escape).
   - EXEC: минимальные привилегии, без исполнения кода от модели, HITL-гейт на критичные действия.
   - INFRA: lock-файлы + audit, потолок трат LLM + лимит вызовов на пользователя.
   - LOGIC: жёсткий system-промпт (роль/границы/анти-jailbreak), тайм-аут + max_tokens, логирование диалога и решений.
   - DATA: секреты только в env, изоляция контекста по пользователю (RLS), маскирование PII, защита от утечки системного промпта.
3. **Сгенерировать код/конфиги** под стек, type-safe, валидация на границах. Минимальная архитектура под MVP.
4. **Зафиксировать** какие контроли заложены и какие осознанно отложены (с причиной) — короткой запиской/в README проекта.

## Принципы (общие для обоих режимов)
- **Разделяй данные и инструкции.** Пользовательский ввод и внешние документы — всегда «данные», не команды. Это корень защиты от INPUT.1/EXEC.3/LOGIC.3.
- **Не доверяй выводу модели.** Валидируй схемой, не исполняй, экранируй перед рендером.
- **Минимальные привилегии везде** — ключи, инструменты, доступ к данным.
- **Человек на критичных действиях** (необратимое/деньги/наружу).
- **Логируй цепочку** — без аудита нет расследования (T8).
- **Считай деньги** — публичный LLM-эндпоинт без потолка = Denial of Wallet.
- Привязывай каждую находку/контроль к `YAISAFE.*` ID и кросс-ссылкам из `catalogs.md` — это делает отчёт сверяемым со стандартами.
