# wrap-session — завершение рабочей сессии NutriMenu

Цель: следующая сессия начинается **за 30 секунд**, открыв `HOME.md` (и `MEMORY.md` auto-memory),
и продолжает РОВНО с места остановки. Не отчёт для архива — рабочая передача контекста себе-будущему.

## Что делает (по порядку)

### 1. Собери факты сессии (НЕ выдумывай)
Пройди по тому, что реально произошло В ЭТОЙ сессии:
- что **зашипано** (коммиты/миграции/файлы — с реальными хешами/именами, если были);
- что **проверено** и каким способом (тест, `/qa`, curl) + результат;
- какие **решения/развилки** закрыты и почему именно так;
- **где ОСТАНОВИЛИСЬ** — самое важное: незавершённый шаг, точка возврата;
- **грабли** — что сломалось и как чинили (чтоб не наступить снова).

**Сверь с реальностью, не с памятью диалога.** Перед записью «✅ сделали» прогони
`git status` + `git log --oneline -3`. Заявление без подтверждения (коммит, существующий
файл, вывод теста из ЭТОЙ сессии) в дейли не пишется — либо проверь, либо пиши «не проверено».
Код в чате ≠ код на диске; «написал» ≠ «закоммитил».

Если чего-то из списка не было — пропусти, не раздувай. Лучше 5 точных строк, чем 30 общих.

### 2. Сверь с внешними находками (аудит/LEARNINGS)
Если в этой сессии закрыт пункт, ранее зафиксированный как проблема во внешнем документе —
разовом аудите (`docs/AUDIT_*.md`, `docs/REPORT_*.md`) или в `LEARNINGS.md` — отметь это явно
**в дейли** («✅ закрыто из находок: <файл>, п. <какой> — <как проверено>»). Сами исходные
файлы правит Юра руками — не редактируй их за него. Без этого шага факт фикса тонет в чате,
а документ продолжает показывать проблему как открытую. Если ничего внешнего не закрывалось — пропусти.

### 3. Определи дату дейли-заметки
Файл — `vault/10-Daily/YYYY-MM-DD.md` за **сегодня** (currentDate из контекста).
- Если файла нет → создай с фронтматтером `---\ndate: YYYY-MM-DD\ntags: [daily]\n---`.
- Если в файле уже есть записи за сегодня (несколько сессий в один день) → **добавь новую
  секцию** `# Сессия N (продолжение) — <тема>` в конец, не перезатирай прошлые.

### 4. Запиши секцию сессии в дейли
Структура (опускай пустые блоки):
```markdown
# Сессия N (продолжение) — <короткая тема>

## ✅ Что сделали / зашипано
- <факт + хеш/файл/миграция>

## 🐞 Грабли (на будущее)
- <что сломалось → как чинили>

## ⏸ ГДЕ ОСТАНОВИЛИСЬ (старт след. сессии)
<одна-две фразы: точная точка возврата + что делать первым>

## 📋 Открытые задачи
0. <следующий конкретный шаг — то, с чего начать>
- <накопленные не-кодовые действия владельца>
- <следующий код по roadmap>
```

### 5. Обнови HOME.md
В `vault/40-MOC/HOME.md`, блок **«## Последнее решение»** — добавь ОДНУ строку
**сверху списка** (свежее первым), формат:
```markdown
- YYYY-MM-DD (сессия N): **<жирный итог одной фразой>.** <2-4 предложения: что сделано,
  где остановились, **старт след. сессии — <что>**. Детали → [[YYYY-MM-DD]] секция «Сессия N».
```
Если в «## Сейчас в фокусе» что-то завершилось или сменилось — поправь там ссылку тоже.

### 6. Обнови auto-memory (project_next_tasks.md)
Живая очередь задач NutriMenu — в auto-memory (`~/.claude/projects/<hash>/memory/`), индекс
`MEMORY.md` подгружается автоматически. Доски задач у проекта нет — вся передача статуса идёт сюда:
- В `project_next_tasks.md` обнови: что закрыто в сессии, текущий статус, **следующий шаг**, блокеры.
  Относительные даты → абсолютные.
- Если появилось новое направление работы, которое переживёт эту неделю → отдельный `project_*.md`
  + строка-указатель в `MEMORY.md` (`- [Заголовок](file.md) — крючок`).
- Не дублируй то, что и так в git/коде. Правь существующий файл, не плоди дубли.

### 7. Обнови код-граф graphify (если код менялся)
Только если в сессии реально менялся код (см. `git status` из шага 1 — не голое планирование).
Инкрементально:
```powershell
graphify . --update
```
Ключи берутся из `.env` / `.env.local` NutriMenu в той же команде PowerShell (env не переживает
между вызовами). Ручной запуск в любой момент никто не отменял — этот шаг страхует от забывчивости.

### 8. Атомарные выводы (если были)
Нетривиальное архитектурное решение / пивот → отдельная заметка в `vault/30-Permanent/`
с `[[wiki-links]]`, и сослаться на неё из дейли. Только если решение переживёт эту неделю.

### 9. LEARNINGS.md (роль Librarian, если уместно)
После нетривиальной фичи/бага (нутриенты, AI-импорт ТТК/штрихкод, Telegram-бот) — 3-5 буллетов
в `LEARNINGS.md` (корень репо). Атомарный урок → почему важно → как применить.

### 10. Пост для соцсетей (build-in-public) — опционально
Если сессия дала осязаемый результат (фича, демо, нетривиальный баг+фикс) и Юра просит —
собери **черновик поста** в конце отчёта. НЕ постить самому — только дать текст.

**Тон — сухой технический build-log** (как Simon Willison / Karpathy: «сделал X, вот что
оказалось»): первое лицо, конкретика вместо общих слов, **без эмодзи и AI-штампов**
(«магия», «уникальный», «seamless»), без CTA-хаков. Не выдумывать цифры — только реально
измеренные в сессии. Русский, human-tone, длина под TG (4-6 коротких абзацев).

## Принципы
- **Относительные даты → абсолютные** (не «завтра», а дата).
- **Точка возврата важнее списка достижений.** Следующая сессия должна знать ПЕРВЫЙ шаг.
- Реальные имена: коммиты, миграции, файлы, env. Без них передача бесполезна.
- Русский, human-tone, по делу. Не дублируй то, что и так в git/коде.
- Не выдумывай прогресс, которого не было. Сомневаешься — спроси одной фразой.

## После записи
Короткое подтверждение пользователю: что обновлено (дейли + HOME + auto-memory + граф,
если менялись) и **с чего начнётся следующая сессия** (процитируй точку возврата).
1-3 строки, без воды.
