## 1. КРИТИЧНЫЕ дыры (cross-cutting) — закрывать первыми

### 🔴 C1. Платные AI-эндпоинты без авторизации и лимита
`parse-ttk`, `validate-ttk`, `parse-pdf-ttk`, `sheets` — **нет `getSession()`, нет rate-limit**, но
внутри вызывают OpenRouter/Gemini нашим ключом. Любой человек с URL может слать POST и жечь бюджет
(cost-abuse) и валить сервис (DoS). Прямо нарушает наше же правило `[[feedback_ai_must_be_gated]]`.
**Подтверждено чтением:** `validate-ttk/route.ts` берёт body и сразу зовёт `validateTTKDishes(...apiKey)`.

### 🔴 C2. Нет rate-limit на дорогих авторизованных роутах
`lookup-barcode`, `lookup-meta`, `ingredients/[id]/enrich`, `import` — авторизованы, но без лимита.
Залогиненный пользователь (или утёкшая кука) может перебором сжечь AI-бюджет. Лимит сейчас стоит
только на 5 роутах: login, register, forgot-password, feedback, feedback/reply.

### 🔴 C3. Сессии нельзя отозвать (stateless JWT, 30 дней)
Сброс пароля не убивает старые сессии; нет «выйти на всех устройствах»; утечёт `AUTH_SECRET` —
отозвать нечем. (Детально разобрано в прошлой сессии.)

### 🟠 C4. Нет `middleware.ts` — авторизация «fail-open»
Админка закрыта только в `app/admin/layout.tsx`, и **это не покрывает `/api/*`**. Каждый из 56
роутов проверяет сессию сам. Новый роут без `getSession()` = открытый эндпоинт, и никто не заметит.

### 🟠 C5. Непоследовательная валидация входа
Только **15 из 56** роутов используют zod. Мутирующие роуты (`items/[id]` PATCH, `ingredients`)
вручную дестректурят JSON и пишут произвольные `Json`-блобы (`composition`, `variantGroups`,
`modifierGroups`) без схемы и без лимита размера → мусор/гигантские payload'ы попадают в БД.

### 🟠 C6. Нет observability
Нет Sentry/error-мониторинга; `console.*` разбросаны (27 мест). В проде мы не видим ошибок —
а это прямой блокер «доверия первых клиентов» (приоритет №1).

### 🟡 C7. Email-доставка под вопросом
Resend — заглушка без домена. Значит письма forgot-password/одобрения, скорее всего, **не доходят**.
Критично для онбординга и сброса пароля.

## 2. По секциям: минусы и риски масштабирования

| Секция | Минусы / дыры | При масштабе |
|---|---|---|
| **S1 Auth** | C3 (нет отзыва), нет 2FA, 30-дн. сессия, один секрет без ротации | управляемо |
| **S2 API** | C4 (нет middleware), C5 (валидация), нет общей обёртки auth+validate+ratelimit+error, ответы об ошибках разнородны | дублирование, дрейф |
| **S3 Dashboard** | `ItemForm`/Community 0 раздут (cohesion 0.05), частично на `useEffect` вместо TanStack | сложно править/тестировать |
| **S4 Admin** | role-проверка копипастой в каждом роуте (C4), bulk-операции без явного аудита | риск пропустить проверку |
| **S5 Public Menu** | per-request DB без кеша/ISR; view-counter — запись на каждый просмотр | **узкое место**: 10 заведений × трафик гостей |
| **S6 Nutrition** | логика в больших `Json`-блобах, не запрашивается на уровне БД; `resolveNutri` — сложная, тесты есть, но покрытие узкое | ок до десятков тыс. блюд |
| **S7 AI-импорт** | C1 (без auth/лимита), синхронный вызов AI в request → риск таймаута Vercel на больших ТТК; нет очереди | таймауты, стоимость |
| **S8 Barcode** | кеш ок; каскад из 5 уровней сложен в поддержке | ок |
| **S9 Plans** | **нет платёжной интеграции** — тарифы есть, оплаты нет; лимиты считаются помесячно полями-счётчиками (`ttkImportMonth`) — гонки при параллельных запросах | блокер выручки (приоритет №2) |
| **S10 Telegram** | самописный state-machine, ручной парсинг апдейтов; webhook защищён secret-token (ок) | хрупкость при росте сценариев |
| **S11 Data** | индексы разумны; но `Json`-блобы мешают аналитике и будущей iiko-синхронизации; нет soft-delete/аудита изменений | iiko-синк будет воевать с Json |
| **S12 Infra** | C6 (нет Sentry), C7 (email), тесты только 5 файлов (нет API/e2e), нет CI-пайплайна кроме pre-push tsc | регрессии незаметны |

## 3. Инвентаризация фич: минусы и варианты улучшения (включая готовые решения)

| Фича | Минус сейчас | Улучшение / библиотека |
|---|---|---|

| **AI-импорт ТТК** | C1 + синхронный AI в HTTP-запросе | gate+limit; перенести в фон-задачу: **Upstash QStash** или Vercel Cron/Queue, статус через polling |

## 4. Поэтапный план (без вреда текущим пользователям)

Принцип безопасности: миграции **аддитивные** (новые поля с дефолтами), гейтинг
обратносовместим (текущие клиенты и так залогинены), рискованное — под фича-флагом.

### Этап 0 — Остановить кровотечение (≈1 день) 🔴
- Навесить `getSession()` + план-гейт + Upstash-лимит на `parse-ttk`, `validate-ttk`,
  `parse-pdf-ttk`, `sheets` (C1).
- Добавить rate-limit на `lookup-barcode`, `lookup-meta`, `enrich`, `import` (C2).
- **Влияние на юзеров:** ноль (легитимные клиенты вызывают эти роуты уже залогиненными).

### Этап 1 — Observability + надёжность (≈2 дня)
- `@sentry/nextjs`, структурные логи (pino), аудит error-boundary.
- **Влияние:** ноль, чистое добавление.

### Этап 2 — Закалка авторизации (≈2–3 дня)
- `tokenVersion Int @default(0)` на `User`, класть в JWT, сверять в `verifySessionToken`,
  бампать при смене пароля → отзыв сессий (C3). Миграция аддитивна.
- `middleware.ts` как defense-in-depth для `/dashboard` и `/admin` (C4).
- Сократить сессию до 7–14 дней; rate-limit на остальные auth-роуты.
- Подключить домен Resend, проверить доставку сброса пароля (C7).
- **Влияние:** старые куки остаются валидны (tokenVersion 0 == 0), без принудительного разлогина.

### Этап 3 — Валидация и целостность данных (≈3–5 дней)
- zod-схемы для всех мутирующих роутов; лимиты размера на `Json`-блобы (C5).
- Общая обёртка роута: `withAuth(withValidation(handler))` — auth+zod+ratelimit+единый формат ошибок.
- Рефакторить роут-за-роутом (обратносовместимо).

### Этап 4 — Перфоманс и масштаб (≈3–5 дней)
- Публичное меню на ISR + `revalidateTag` при правке меню; view-counter — Redis-инкремент.
- Пагинация списков (admin venues, items), ревизия запросов на N+1.
- Доделать миграцию `/dashboard/*` с `useEffect` на TanStack Query.

### Этап 5 — Выручка (приоритет №2)
- Интеграция оплаты (ЮKassa): checkout → вебхук → `paidUntil`/`plan`. Атомарные лимиты.

### Этап 6 — iiko-интеграция (отдельная крупная задача, ПОСЛЕ Этапа 3)
- Зависит от чистой валидированной схемы и идемпотентных upsert'ов.
- Нужна таблица маппинга внешних id (`ExternalRef`: provider=iiko, externalId↔menuItemId/categoryId),
  сервис синхронизации (pull меню/стоп-листов), очередь и конфликт-резолюция.
- `Json`-блобы КБЖУ ⇄ номенклатура iiko — отдельный слой трансформации.
